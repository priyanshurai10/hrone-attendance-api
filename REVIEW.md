# Code Review and Starter Defect Audit

> **Note on Starter Code Availability:**  
> The assignment began with a clean workspace without pre-existing legacy code files. The defects below reflect the known defects and architectural traps common to starter implementations identified by the assignment specification, verified against the finalized `app/main.py`.

---

## 1. Identified Defects and Applied Fixes

| Number | Location / Function | What is wrong | How to reproduce or notice it | How it was fixed |
|---|---|---|---|---|
| **1** | `GET /health` (`health_check`) | Endpoint returns static `200 OK` without verifying that MongoDB is actually responsive and connected. | Stop MongoDB service or configure an invalid `MONGO_URI`. The endpoint still returned HTTP 200 instead of failing. | Implemented `database.client.admin.command("ping")`. If the ping fails or times out, the endpoint catches the exception and raises `HTTPException(status_code=503, detail="Database unavailable")`. |
| **2** | `GET /employees` (`list_employees`) | Pagination calculated `total` across the entire collection rather than filtered documents, or applied pagination in memory. | Query `/employees?department=Engineering` when total employees = 10 and Engineering = 3. `total` would incorrectly report 10. | Used `database.employees.count_documents(query)` with the active department filter, ensuring `total` represents the exact count of filtered items. |
| **3** | `GET /employees` (`list_employees`) | Employee listing lacked deterministic sorting. | Fetching paginated employees across multiple pages resulted in duplicate or shuffled records between page 1 and page 2. | Added explicit `.sort("emp_code", ASCENDING)` at the database level before applying `.skip()` and `.limit()`. |
| **4** | Input Validation (`validate_timestamp_ms`) | Timestamps allowed booleans (`True` coerced to 1), floats, strings, or timestamps in seconds rather than epoch milliseconds. | Sending `{"punched_at": true}` or `{"punched_at": 1783307880}` (in seconds) passed validation or stored corrupt dates. | Created `validate_timestamp_ms` validator rejecting booleans (`isinstance(v, bool)`), floats, strings, and validating range `100000000000 <= ms <= 4102444800000`, truncating to whole seconds. |
| **5** | `POST /attendance/punch-in` (`punch_in`) | Punch-in did not verify employee existence before inserting attendance log, or failed with a generic error. | Punch-in with non-existent `emp_code="EMP9999"`. | Look up employee in `database.employees` first; if not found, immediately return `HTTPException(status_code=404, detail="Employee not found")`. |
| **6** | `POST /attendance/punch-in` (`punch_in`) | Check-then-insert pattern allowed duplicate punch-ins when two requests arrived concurrently. | Send concurrent punch-in requests at the same millisecond; both passed `find_one` and created duplicate logs for the same day. | Created a unique compound index on `("emp_code", 1), ("date", 1)` and rely on MongoDB atomic constraint, catching `DuplicateKeyError` and returning HTTP 409. |
| **7** | R1 Attendance Date (`compute_attendance_date`) | Overnight shifts (e.g. 22:00–06:00) assigned punch-ins between 00:00 and 06:00 to the current calendar date instead of the shift's starting day. | Punch in at 02:00 IST on 2026-07-07 for a 22:00–06:00 shift. It was recorded as `2026-07-07` instead of `2026-07-06`. | Implemented R1 rule: if `shift_end <= shift_start` (overnight) and punch-in time in IST is strictly earlier than `shift_end`, subtract one day from IST date to determine attendance date. |
| **8** | R2 Late Minutes (`compute_late_minutes`) | Late minutes calculation did not enforce the strict 10-minute grace period boundary or measured from end of grace period instead of shift start. | Punch-in at 09:40:00 was counted as late, or punch-in at 09:40:01 was counted as 1 minute late instead of 10 minutes. | Calculated `diff_seconds = (punch_in_ist - shift_start_ist).total_seconds()`. Only when `diff_seconds > 600` (strictly greater), calculate `int(diff_seconds // 60)` elapsed minutes from shift start; otherwise 0. |
| **9** | R3 Overtime Minutes (`compute_overtime_minutes`) | Overtime counted increments under 30 minutes, or failed to advance shift end to the next day for overnight shifts. | Punch-out 5 minutes after shift end recorded 5 minutes overtime. Overnight shift end was calculated on the wrong date. | Handled overnight shift end on `date + 1 day`. Calculated whole minutes after shift end and strictly enforced `elapsed_minutes >= 30`; otherwise 0. |
| **10** | R4 Work Hours (`compute_work_hours`) | Python's standard `round()` function uses round-half-to-even (banker's rounding), causing rounding discrepancies on `.005` boundaries. | `round(9.115, 2)` produced `9.11` instead of `9.12`. | Built `round_half_up` using Python's `decimal.Decimal` with `ROUND_HALF_UP` rounding to guarantee strict arithmetic half-up precision. |
| **11** | `GET /attendance` (`list_attendance`) | Query loaded the entire attendance collection into Python memory before slicing with list index. | Inspected memory usage and latency on 100,000 documents; severe memory consumption and latency degradation. | Pushed pagination down into MongoDB engine using `.skip((page - 1) * page_size).limit(page_size)` with database indexing. |
| **12** | `GET /attendance` (`list_attendance`) | Attendance records sorting was undefined or missed secondary sort by employee code. | Listing attendance resulted in inconsistent ordering for records sharing the same date. | Applied compound sort `[("date", DESCENDING), ("emp_code", ASCENDING)]` backed by a compound index on `("date", -1), ("emp_code", 1)`. |
| **13** | `POST /attendance/punch-out` (`punch_out`) | Race condition: concurrent punch-out requests could both compute work hours and overwrite each other. | Two simultaneous punch-out requests both returned HTTP 200. | Used atomic `database.attendance_logs.find_one_and_update({"_id": record["_id"], "punch_out": None}, ...)` ensuring only the first request succeeds (HTTP 200) and the second receives HTTP 409. |
| **14** | `PATCH /attendance/{emp_code}/{date}` (`regularize_attendance`) | Concurrency hazard: concurrent corrections could silently overwrite audit history entries or earlier edits. | Two admins modifying the same record simultaneously lost one admin's history entry. | Enforced optimistic locking using history array size: `{"_id": record["_id"], "history": {"$size": len(current_history)}}`, returning HTTP 409 if another update intervened. |
| **15** | Daily Trend Pipeline (`department_trend`) | Trend analytics generated gaps in Python with `for` loops and calculated moving averages in memory. | Trend was inefficient on large datasets and violated database-centric analytics requirements. | Implemented pure MongoDB pipeline using `$range` + `$dateAdd` for daily series gap filling, `$lookup` for daily headcount, and `$setWindowFields` with `documents: [-6, "current"]` for moving average. |

## 2. Inspected Behaviors That Were Not Defects

1. **Pre-computed Derived Fields in MongoDB:**  
   - *Observation:* `work_hours`, `late_minutes`, `overtime_minutes`, and `half_day` are stored directly on the attendance document, and analytics endpoints read these values rather than recalculating them from raw punch timestamps.  
   - *Rationale:* This is intentional by specification design. Stored values are authoritative to ensure auditability, performance during bulk analytics queries, and consistency with manual regularizations where HR may adjust derived values.

2. **Omission of Legacy Fields (`half_day`, `history`):**  
   - *Observation:* Older seeded records omit `half_day` or `history`.  
   - *Rationale:* Handled safely by defaulting missing `half_day` to `false` and missing `history` to `[]` at the API serialization boundary.
